# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A dengue surveillance tool for Sri Lankan public health divisions. Residents report
mosquito breeding sites; officers work an inspection queue and notify confirmed cases. The
point of the application is the **risk model** that crosses those two streams — see
"The risk model" below, which is the part most likely to be broken by an innocent-looking
change.

## Layout

Two independent apps in one repo:

- `backend/` — ASP.NET Core 8 Web API (`HackathonApi`), controller-based, EF Core + Npgsql
- `frontend/` — React 19 + Vite 8, JavaScript (no TypeScript), Tailwind CSS v4

The two use deliberately different folder conventions. The backend is **layer-based**
(`Controllers/`, `Services/`, `Data/`, `Dtos/`, `Models/`, `Middleware/`); the frontend is
**feature-based** (`src/features/<feature>/`, with `src/shared/`, `src/app/`, `src/api/`).
Keep new code in the convention of the side it belongs to.

## Commands

```bash
# Backend — serves on http://localhost:5116, Swagger UI at /swagger
cd backend && dotnet run
cd backend && dotnet build

# Migrations (dotnet-ef is installed globally)
cd backend && dotnet ef migrations add <Name>
cd backend && dotnet ef database update
cd backend && dotnet ef migrations list        # read-only connectivity check

# Frontend — serves on http://localhost:5173
cd frontend && npm run dev
cd frontend && npm run build
cd frontend && npm run lint                    # oxlint, not eslint
```

There is no test suite in either project. `.claude/launch.json` at the repo root starts the
frontend dev server for preview tooling.

## Domain

Three entities, in `backend/Models/`:

- **`Division`** — a public health area (`Name`, `MohArea`, `District`). The unit risk is
  scored on.
- **`Report`** — a reported breeding site: `SiteType`, `DivisionId`, description, landmark,
  reporter name and phone, `Status`, `ReportedAt`, `InspectedAt`, `InspectorNote`,
  `IsAutoGenerated`.
- **`DengueCase`** — a confirmed case: `DivisionId`, `ReportedDate`, `AgeBand`, `Severity`,
  `Hospitalised`.

**`DengueCase` holds no patient name, address or contact details, and that is deliberate.**
Do not add them. `ReportDto` likewise omits `ReporterPhone` — the number is collected so an
inspector can follow up, not so it can be served to every dashboard client.

Enums live in `Models/Enums.cs`: `SiteType`, `ReportStatus`, `AgeBand`, `CaseSeverity`,
`RiskBand`.

## The risk model

**All risk logic lives in `Services/IRiskService` / `RiskService`. Nothing else in the
codebase may re-implement or second-guess any part of it.** Weights, thresholds, multipliers
and the band → action strings are all there, as public constants so they can be tuned in one
place. `RiskService` is pure — it takes rows and returns numbers, and applies its own status
and date filters regardless of what a caller hands it.

Two independent axes:

- **`vectorRisk`** — sum of `siteTypeWeight × ageingMultiplier` over a division's open
  reports. A leading indicator: habitat that exists before anyone is ill.
- **`transmissionRisk`** — cases in the division in the last 14 days. A lagging indicator.

Crossing them at `vectorRisk >= 20` and `cases >= 8` gives the four bands: Emergency,
Prevent, Investigate, Monitor.

Three invariants that are easy to break:

- **"Open" means `Reported` or `Inspected` only.** `Cleared` and `NoticeIssued` score 0 — a
  notice means the case has moved to enforcement, not that habitat is still being counted.
  Ask `IRiskService.IsOpenReport`; never test `ReportStatus` yourself.
- **Auto-generated reports are excluded from vector risk and from `openReportCount`.**
  Notifying a case creates an inspection report (below). If those scored, transmission risk
  would feed back into vector risk, the two axes would stop being independent, and the
  Investigate band — which exists precisely to flag *cases without reports* — could never be
  reached. This exclusion is the reason the quadrant model works.
- **The ageing thresholds are epidemiological, not arbitrary.** 7 days is the *Aedes aegypti*
  egg-to-adult cycle; 14 days is two cycles; the 14-day case window is one mosquito
  generation plus incubation and illness onset. The XML docs on each constant carry the
  reasoning — keep them in sync if the numbers change.

`SiteType.PremisesInspection` is a non-container member carried only by auto-generated
reports. It has weight 0 and is deliberately absent from the frontend's report form.

## Backend architecture

**Request flow:** `Controllers/` → `Services/` → `Data/AppDbContext`. Controllers are thin —
each action does a `ModelState` check and one service call. All EF queries and business logic
live in `Services/`. Services return DTOs and never leak entities to the caller.

**Errors are exceptions, not result types.** A service throws
`Middleware/NotFoundException` when an id doesn't resolve, or `Middleware/BadRequestException`
when a well-formed request cannot be honoured (a duplicate officer email, a change that would
remove the last active Admin); `ExceptionHandlingMiddleware` translates them to a 404 and a 400. Controllers do not check for null and do not return `NotFound()`
themselves. That middleware is registered **first** in the pipeline so it wraps everything,
and emits `{ message, detail }` — `detail` carries the stack trace outside Production and is
`null` in Production. Note that a create against an unknown `DivisionId` also throws
`NotFoundException`, so it surfaces as 404 rather than 400.

**Enums are stored and transmitted as strings.** `AppDbContext` maps them with
`.HasConversion<string>()` so Postgres holds `'NoticeIssued'`, and `Program.cs` registers
`JsonStringEnumConverter` so the API emits `"NoticeIssued"` too. Changing one without the
other splits the wire format from the storage format. `DashboardDto.DivisionsByBand` is keyed
by the `RiskBand` enum; .NET writes enum dictionary keys as names.

**Notifying a case also opens a report.** `CaseService.CreateAsync` writes the case *and* a
premises-inspection `Report` in the same division and the same `SaveChanges`, mirroring the
MOH case-investigation process. It carries `IsAutoGenerated = true`,
`SiteType.PremisesInspection` and `ReporterName = "System (case notification)"`.

**Reports are sorted by risk score, in memory.** The score is computed rather than stored, so
the ordering cannot be pushed into SQL: `ReportService` materialises the filtered set, scores
it, sorts, then pages. Correct, but it loads every matching row. If report volume ever grows
past a few thousand per query, persist the score and sort in the database.

**Search uses `EF.Functions.ILike`** (Postgres-native case-insensitivity) over description and
landmark, with `%` and `_` escaped so user input can't act as a wildcard. This is Npgsql-only
— it will not run against a SQLite test harness.

**`?phone=` on `GET /api/reports` is an exact match, not a search.** It is what `/my-reports`
runs on: with no sign-in, a resident finds their own submissions by typing the number they
filed under, so a prefix match would hand them somebody else's reports. The parameter is
validated against the same `^0[0-9]{9}$` rule as `CreateReportDto.ReporterPhone`, and
`ReportDto` still never returns the number.

**Foreign keys use `DeleteBehavior.Restrict`.** A division with reports or cases against it
must be reassigned before it can be removed, rather than silently taking its history along.

**Swagger is enabled in every environment**, not gated on Development. CORS policy
`AllowFrontend` allows any origin/header/method and is applied before `MapControllers`.

### DTO conventions

Read DTOs are positional records; write DTOs are `{ get; init; }` records with an
`ErrorMessage` on every DataAnnotation.

- **Required enums on create DTOs are nullable** (`SiteType?`, `AgeBand?`, …). `[Required]` on
  a non-nullable enum is inert — the field always has a value — so omitting it from the JSON
  would silently create a report of whatever the first enum member happens to be. Services
  read `dto.SiteType!.Value` behind the `ModelState` guard.
- **Required ids use `[Range(1, int.MaxValue)]`**, which rejects the 0 a missing int arrives as.
- **`Dtos/NotInTheFutureAttribute`** is a custom validator; DataAnnotations has no
  "not after now". It normalises to UTC and allows 5 minutes of clock skew.

### Authentication

**Officers sign in; residents never do.** `POST /api/auth/login` verifies a BCrypt hash and
issues an 8-hour JWT carrying officer id, email, role and MOH area. `GET /api/auth/me` is what
the frontend calls on start-up to find out whether a stored token still works.

- **The signing key comes from `JWT_SECRET`**, falling back to `Jwt:Secret` in the gitignored
  `appsettings.Development.json`. `Services/JwtSettings.cs` resolves it in one place, used by
  both `Program.cs` (validating) and `AuthService` (issuing), and **throws at startup** if it
  is missing or under 32 characters — a generated default would sign tokens that stop
  validating on the next restart, and a hard-coded one would ship a public secret.
- **Login answers "Invalid email or password." for both a wrong password and an unknown
  address**, so the endpoint cannot be used to enumerate which emails hold accounts. It also
  runs a BCrypt verify against a throwaway hash when the account is missing, so the two cases
  take similar time. A *deactivated* account is told so plainly — by then the password was
  right, and there is nothing left to conceal.
- **Two guard rails in `OfficerService`, both enforced server-side:** an officer cannot
  deactivate their own account, and no change may leave the system without an active Admin
  (deactivating *or* demoting the last one is refused). The frontend shows those 400s verbatim
  rather than predicting them — only the server knows the current count.
- **`/auth/me` re-checks `IsActive`.** A token outlives a deactivation, so the account is
  verified on each restore rather than trusted because it was valid when signed.

**The authorisation split:**

| Surface | Access |
| --- | --- |
| Landing page, `GET /api/divisions`, `GET /api/risk-model` | anonymous |
| `POST /api/reports`, `GET /api/reports/by-phone` | anonymous |
| `GET /api/reports` (queue), status updates, cases, `GET /api/divisions/dashboard` | `[Authorize]` |
| `/api/officers` | `[Authorize(Roles = "Admin")]` |

Two consequences worth knowing. **`GET /api/reports/by-phone` exists as a separate endpoint**
rather than an anonymous `?phone=` on the queue, so no anonymous caller reaches the full list
by omitting a filter. And **the landing page reads `GET /api/divisions`, not the dashboard** —
its three headline figures are sums of the per-division counts that endpoint already publishes.

### Startup, migration and seeding

`Program.cs` runs `db.Database.Migrate()` and then `DbSeeder.SeedAsync(db)` in a scope before
the pipeline is built, so a fresh database is ready on first run.

**`Data/DbSeeder.cs` is hand-tuned, not randomised, and that matters.** Four divisions are
engineered to land in one risk quadrant each so the demo tells a story: Kolonnawa
→ Emergency, Maharagama → Prevent, Wattala → Investigate, Negombo → Monitor. The other four
sit mid-range (all of which band as Monitor, since middling values cross neither threshold).
Changing the report counts, statuses or case counts changes what the dashboard shows. Dates
are expressed as "days ago" against the current UTC date so seeded data stays inside the
trailing 30-day window on every run.

Seeding guards each table independently and is a no-op once anything has been written. It also
lays down three officer accounts (`admin@moh.lk` as Admin, plus two Officers) sharing the
password `Dengue@2026`, and prints them to the console on the run that creates them — the
hashes are one-way, so there is no other way to discover them.

### Database connection

The connection string is read from `ConnectionStrings:DefaultConnection`, but
`Program.cs` explicitly prefers the `ConnectionStrings__DefaultConnection` environment
variable when set, so deployments can inject it without touching config files. Local
credentials live in `backend/appsettings.Development.json`, which is **gitignored** —
a fresh clone has no working connection string and must be given one.

Currently pointed at Supabase. Two non-obvious constraints apply there:

- The direct host (`db.<ref>.supabase.co`) is **IPv6-only**. On an IPv4-only network it fails
  with a DNS "no answer" for the A record. Use the Supavisor pooler host
  (`aws-0-<region>.pooler.supabase.com`) instead.
- The pooler requires a **tenant-qualified username** — `postgres.<project-ref>`, not bare
  `postgres`. Port 5432 is session mode (required for EF migrations); 6543 is transaction
  mode and additionally needs `No Reset On Close=true;Max Auto Prepare=0`.

Npgsql rejects a non-UTC `DateTime` for its `timestamp with time zone` columns. Anything
reaching the database must have `Kind == Utc` — `CaseService.ToUtc` and `DbSeeder.DaysAgo`
both exist for that reason.

## Frontend architecture

**`src/api/client.js` changes the shape of every API call.** A response interceptor returns
`response.data`, so functions in the feature `api/` modules resolve to the payload directly —
there is no `.data` to unwrap at the call site. An error interceptor rejects with a normalised
`{ message, fieldErrors, status }`, where `fieldErrors` is ASP.NET Core's ProblemDetails
`errors` object flattened and **camelCased** so a form can look up an error by input `name`.
Callers should read `err.message` and `err.fieldErrors`, never `err.response`.

**Features:** `reports/`, `divisions/`, `cases/`, each with an `api/` module and `pages/`
(plus `components/` where a table or card is shared), and `about/`, which is prose only and so
has `pages/` alone; `auth/` (the login page) and `officers/` (admin account management). `src/shared/` holds presentation-only primitives
with **no API, router or feature knowledge** and is re-exported from `src/shared/index.js` —
importing a feature module from `shared/` is the mistake to avoid.

**Auth is real, and the frontend is not where it is enforced.** `src/app/AuthContext.jsx`
holds the token and officer, persists both to localStorage, and confirms them against
`/auth/me` on mount — dropping the session if that fails. `ProtectedRoute` (with an `adminOnly`
variant) keeps unauthenticated users out of the officer routes and preserves where they were
heading, so login can send them on. All of that is a convenience: the API refuses the same
requests regardless of what the frontend renders.

**`src/api/client.js` attaches the token and handles 401 centrally.** A request interceptor
adds `Authorization: Bearer …`; a response interceptor clears the session and navigates to
`/login` on a 401, skipping the redirect when already there. Both read storage through
`src/api/authToken.js` rather than React state, so the interceptors and the context cannot
disagree about the key.

**Routes** (`src/app/router.jsx`): `/` risk board, `/report`, `/my-reports`, `/about`, and
`/login`, officer-gated `/queue` (`InspectionQueuePage`), `/cases` (`RecordCasePage`),
`/dashboard`, and admin-gated `/officers` (`OfficerManagementPage`).

**`/my-reports` is a phone lookup.** There is no resident sign-in, so "mine" means every report
filed under a number they type back in — one anonymous `GET /api/reports/by-phone` call. The last
number used is kept in localStorage (`dengue.myReportPhone`) so submitting a report leads to a
prefilled, auto-run lookup, but the number is deliberately kept out of the URL: unlike
`QueuePage` and `CasesPage`, this view must not put its state in `useSearchParams`, or a shared
link would carry somebody's phone number.

**Tailwind v4 — there is no `tailwind.config.js`.** It's wired through the
`@tailwindcss/vite` plugin, and the design tokens are declared in an `@theme` block at the top
of `src/index.css`. Add or change colours there, not in a config file.

**Styling goes through semantic tokens.** Components use `bg-surface`, `text-ink`,
`text-ink-muted`, `border-line`, `bg-accent-soft` and so on — never raw Tailwind palette
colours like `bg-gray-100`. The palette is one neutral ramp plus a single accent. Colour
carries meaning in exactly two places, both badge components:

- **`RiskBadge`** — Emergency `danger`, Prevent `warn`, Investigate `study`, Monitor `accent`.
  The mapping is the component's whole purpose and is not caller-configurable.
- **`StatusBadge`** — report workflow status, deliberately quieter so it doesn't compete with
  the risk banding beside it.

`Badge` is a neutral tone-based chip for everything else. Keep to the existing type scale
(`text-xs`/`sm`/`base`/`lg`/`xl`) rather than introducing intermediate sizes.

**List state lives in the URL.** `InspectionQueuePage` and `RecordCasePage` read filters and
page from `useSearchParams` rather than component state, so views survive refresh and can be
shared. Text inputs are debounced through `shared/useDebounced.js` (the queue search passes
300ms) before hitting the API.

**The queue renders twice: a table from `md` up, cards below it.** Both halves of
`InspectionQueueList` drive the same `ReportDetailPanel` — the full description, the reporter's
name and the status control — so an officer works the same way on a phone as at a desk. A
status change is followed by a full refetch rather than a local patch, because the change moves
the report's risk score and the queue is ordered by it.

**`reportsApi.AGEING_THRESHOLD_DAYS` mirrors `RiskService.AgeingThresholdDays`.** It is the one
number duplicated across the two sides, and it is used only to flag rows that have been open
past a mosquito generation — the scoring itself stays entirely on the backend. If the backend
constant moves, move this one too.

**The dashboard's quadrant matrix reads its content off the data.** `QuadrantMatrix` places
divisions by the `riskBand` the API returned and takes each cell's action text from the
divisions that landed in it, so neither the thresholds nor the band → action strings are
restated on the frontend. The Investigate cell is deliberately drawn louder than the other
three: it is the quadrant the crossed-axes model exists to surface.
